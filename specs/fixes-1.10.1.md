# Исправления 1.10.1: настройки топика и брокера, ребалансировка, идентификатор кластера

Статус: реализовано 2026-10-15 (шаги 1–5), не закоммичено.
Версия компоненты: 1.10.1.

## 1. Цель

Исправить три ошибки, найденные сверкой компоненты с API librdkafka 2.16.0. Новых методов нет.

## 2. Ошибки

### 2.1. `УстановитьНастройкиТопика` и `УстановитьНастройкиБрокера` сбрасывают чужие настройки

`src/admin_topics.cpp`, `setTopicConfig` и `setBrokerConfig`, вызывают `rd_kafka_AlterConfigs`
только с ключами из JSON. Документация `rdkafka.h`: «AlterConfigs will replace all existing
configuration for the provided resources with the new configuration given, reverting all other
configuration to their default values», функция помечена
`@deprecated Use rd_kafka_IncrementalAlterConfigs()`.

Следствие: у топика с `cleanup.policy=compact` вызов
`УстановитьНастройкиТопика(Брокеры, Топик, "{""retention.ms"": ""86400000""}")` возвращает
`cleanup.policy` к значению по умолчанию (`delete`) — тихая потеря данных компактируемого топика.
Документация методов в `docs/admin.md` об этом не предупреждает.

### 2.2. Ребалансировка после `УстановитьПозициюЧтения`

`src/SimpleKafka1C.cpp`, `clRebalanceCb::rebalance_cb`. Обработчик подключается только если до
`ИнициализироватьКонсьюмера` вызывались `УстановитьПозициюЧтения` / `УстановитьПозицииЧтения`.
При подключённом обработчике назначение партиций выполняет он, а не librdkafka.

- При первом назначении он применяет позиции, вызывает `assign()` и очищает список позиций.
  При **следующем** назначении (вошёл или вышел другой участник группы) список пуст, и
  `assign()` не вызывается: консьюмер остаётся без партиций и перестаёт получать сообщения,
  ошибок нет.
- При `partition.assignment.strategy=cooperative-sticky` и при `group.protocol=consumer`
  (KIP-848) librdkafka требует `incremental_assign()` / `incremental_unassign()`. Вызов
  `assign()` / `unassign()` в этом режиме — ошибка протокола (`RD_KAFKA_RESP_ERR__STATE`),
  консьюмер не получает партиции.

### 2.3. `ПолучитьИнформациюОКластере` возвращает не идентификатор кластера

`src/admin_metadata.cpp`, `getClusterInfo`: `cluster_id` заполняется
`metadata->orig_broker_id()` — это id брокера, ответившего на запрос метаданных, а не
идентификатор кластера. В `docs/admin.md` поле так и описано («ID брокера, к которому выполнено
подключение»), то есть ошибка в имени поля, а не только в коде. Настоящий идентификатор кластера
(строка вида `MkU3OEVBNTcwNTJENDM2Qg`) даёт `RdKafka::Handle::clusterid()`.

## 3. Требуемое поведение

### 3.1. Настройки топика и брокера

- Оба метода используют `rd_kafka_IncrementalAlterConfigs`: каждый ключ из JSON —
  операция `SET`; не указанные ключи не меняются.
- Значение `null` в JSON — операция `DELETE`: настройка возвращается к значению по умолчанию
  (раньше это происходило с любым не указанным ключом; теперь — только явно).
  Пример: `{"retention.ms": "86400000", "max.message.bytes": null}`.
- Типы значений как раньше: строка, целое, булево, дробное. Значения других типов (массив,
  объект) → ошибка с именем ключа (раньше молча пропускались).
- Ошибка по ресурсу — текст `rd_kafka_ConfigResource_error_string`, как раньше.
- Сигнатуры методов не меняются. Требуется брокер Kafka 2.3+ (IncrementalAlterConfigs).

### 3.2. Ребалансировка

- Обработчик определяет протокол через `consumer->rebalance_protocol()`:
  `"COOPERATIVE"` → `incremental_assign` / `incremental_unassign` с переданными партициями;
  иначе (`"EAGER"`, пусто) → `assign` / `unassign`.
- Назначение выполняется **всегда**, при любом количестве сохранённых позиций.
- Семантика позиций не меняется: применяются при первом назначении к совпавшим партициям,
  затем список очищается.
- Ошибки `assign`/`incremental_*` пишутся в лог консьюмера и в асинхронную ошибку
  (`ПолучитьСообщениеОбОшибке`).
- Обработчик подключается **всегда** (решение 3), а не только при заданных позициях.

### 3.3. Идентификатор кластера

- `cluster_id` — строка, результат `clusterid(5000)`; если брокер его не вернул — пустая строка.
- Добавляется поле `orig_broker_id` — прежнее значение `cluster_id`. В JSON это строка, как
  и остальные поля ответа (сериализация `boost::property_tree`).
- Остальные поля без изменений.

## 4. Критерии приёмки

Стенд: `docker/kafka-share` (Kafka 4.2.2, один брокер). Проверки — в `tests/native-harness`.

**AC-1. Не указанные настройки топика сохраняются**
Given топик с `cleanup.policy=compact`, установленным через `УстановитьНастройкиТопика`
When `УстановитьНастройкиТопика(..., "{""retention.ms"": ""86400000""}")`
Then `ПолучитьНастройкиТопика` показывает `retention.ms=86400000` и `cleanup.policy=compact`.
(До исправления — `cleanup.policy=delete`: harness сначала подтверждает ошибку на 1.10.0.)

**AC-2. Сброс настройки через null**
Given у топика `retention.ms=86400000`
When `УстановитьНастройкиТопика(..., "{""retention.ms"": null}")`
Then `retention.ms` равен значению по умолчанию, `cleanup.policy` не изменился.

**AC-3. Неверный тип значения**
When в JSON значение — массив
Then возврат Ложь, ошибка содержит имя ключа, настройки топика не изменились.

**AC-4. Настройки брокера**
Given динамическая настройка брокера A установлена через `УстановитьНастройкиБрокера`
When установить настройку B
Then A сохранила значение; после `{"A": null, "B": null}` обе вернулись к умолчанию.

**AC-5. Повторная ребалансировка с позициями чтения (eager)**
Given топик с 2 партициями, консьюмер A с `УстановитьПозициюЧтения` до инициализации читает
When в группу входит консьюмер B, затем B выходит, и в топик пишутся новые сообщения
Then A получает новые сообщения после каждой ребалансировки; позиция применилась один раз.
(До исправления — A после второй ребалансировки ничего не получает.)

**AC-6. cooperative-sticky**
Given `partition.assignment.strategy=cooperative-sticky`, позиции чтения заданы
When сценарий AC-5
Then позиция применена, A и B вместе читают все сообщения, ошибок назначения нет.

**AC-7. KIP-848 (`group.protocol=consumer`)**
Given `group.protocol=consumer`, позиции чтения заданы
When сценарий AC-5
Then как в AC-6.

**AC-7a. Выход из группы при cooperative-sticky**
Given консьюмер B без позиций чтения, `partition.assignment.strategy=cooperative-sticky`
When `ОстановитьКонсьюмера` у B
Then B отправляет LeaveGroup, и его партиции переходят к A раньше `session.timeout.ms` (45 с).
(До исправления — B выпадал из группы только по таймауту сессии; проверяется в FIX-6.)

**AC-8. Идентификатор кластера**
When `ПолучитьИнформациюОКластере(Брокеры)`
Then `cluster_id` совпадает с `rd_kafka_clusterid()` (harness получает его напрямую),
`orig_broker_id` — id брокера стенда.

**AC-9. Регрессия**
Полный прогон harness (сценарии очередей и AC-18 обычного consumer/producer) — без ошибок.

## 5. Документация

- `docs/admin.md`: `УстановитьНастройкиТопика` и `УстановитьНастройкиБрокера` — меняются только
  указанные ключи, `null` сбрасывает настройку, пример на 1С; `ПолучитьИнформациюОКластере` —
  новое описание `cluster_id` и поле `orig_broker_id`.
- `docs/consumer.md`: у `УстановитьПозициюЧтения` — работа с cooperative-sticky и KIP-848.
- `CHANGELOG.md`: 1.10.1, раздел «Исправлено»; изменение смысла `cluster_id` отмечено отдельно;
  выход из группы при `cooperative-sticky` (AC-7a).

## 6. Решения (2026-10-15)

1. `cluster_id` — настоящий идентификатор кластера, прежнее значение — в `orig_broker_id`;
   документация `docs/admin.md` исправляется, изменение отмечается в CHANGELOG.
2. Сброс не указанных ключей считается ошибкой; сброс к умолчанию — только явно через `null`.
3. Обработчик ребалансировки подключается всегда. Причина: в librdkafka 2.16.0 консьюмер с
   `cooperative-sticky` (классический протокол) без `rebalance_cb` при `close()` не отправляет
   LeaveGroup (`rd_kafka_cgrp_incr_unassign_done` при завершении → полный unassign при пустом
   назначении → состояние `term` без `rd_kafka_cgrp_leave`). Партиции такого консьюмера
   простаивают до `session.timeout.ms`. С обработчиком компоненты LeaveGroup уходит.
