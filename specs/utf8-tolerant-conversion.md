# Спецификация: устойчивая конвертация UTF-8 → UTF-16 при передаче данных в 1С

Статус: черновик, ожидает утверждения
Связанные проблемы: падение процесса 1С (`addnhost64`, Linux) при чтении сообщений с невалидным UTF-8

## 1. Проблема

При чтении сообщений из Kafka на Linux процесс сервера 1С аварийно завершается:

```
terminate called after throwing an instance of 'std::range_error'
  what():  wstring_convert::from_bytes
```

С точки зрения прикладного кода 1С метод чтения «висит» до истечения таймаута и
возвращается без сообщений, хотя в логах librdkafka видно и назначение партиций
(`BEGINNING`), и постановку батча в очередь (`Enqueue ... offset ...`).

### Цепочка отказа

1. `SimpleKafka1C::getMessageData(binaryResult = Ложь)` (`src/consumer_methods.cpp:728`)
   и устаревший `SimpleKafka1C::consume()` (`src/consumer_methods.cpp:455`)
   возвращают тело сообщения как `std::string` — байт в байт, без проверки кодировки.
2. `Component::CallAsFunc` конвертирует результат в UTF-16 вызовом
   `storeVariable(result, *ret_value)` — `src/Component.cpp:274`.
3. `Component::toUTF16String(std::string_view)` (`src/Component.cpp:494`) выполняет
   конвертацию через `std::wstring_convert::from_bytes`. На невалидной
   UTF-8 последовательности (Avro, Protobuf, произвольный бинарь, CP1251)
   реализация libstdc++ бросает `std::range_error`.
4. Вызов `storeVariable` на строке 274 находится **вне** блока `try`, закрытого на
   строке 266. Исключение покидает `CallAsFunc` и пересекает границу C-ABI
   платформы 1С, что приводит к `std::terminate` и падению процесса.

Тот же дефект присутствует в `Component::GetPropVal` (`src/Component.cpp:114`, `:198`),
где `storeVariable` также вызывается без охватывающего `try`.

На Windows (MSVC) шаг 3 на тех же данных ведёт себя иначе, поэтому падения не происходит
и клиент успевает вычитать очередь — отсюда расхождение поведения между платформами.

### Существующая частичная защита

Пакетные методы чтения (`src/consumer_methods.cpp:634` и `:890`) уже используют
`putUtf8OrBase64` поверх `isValidUtf8` (`src/utils.cpp:34`) и подменяют невалидное тело
на base64, проставляя поле `message_encoding`. Одиночные методы чтения такой защиты
не имеют.

### Сопутствующий дефект

`src/consumer_methods.cpp:441` и `:518` читают значение заголовка сообщения как
NUL-терминированную C-строку, игнорируя `hdr.value_size()`. Для бинарных значений
заголовка это чтение за границей буфера librdkafka.

## 2. Требования

### R1. Конвертация UTF-8 → UTF-16 не бросает исключений на некорректных данных

`Component::toUTF16String(std::string_view)` должен быть толерантным: каждая
невалидная байтовая последовательность заменяется на U+FFFD (REPLACEMENT CHARACTER),
конвертация продолжается до конца входного буфера.

### R2. Конвертация UTF-16 → UTF-8 не бросает исключений

`Component::toUTF8String(std::basic_string_view<WCHAR_T>)` аналогично: непарные
суррогаты заменяются на U+FFFD.

### R3. Исключение никогда не покидает точку входа компоненты

`storeVariable` в `CallAsFunc` и `GetPropVal` должен вызываться внутри `try`/`catch`.
При ошибке возвращается пустое/ложное значение, текст ошибки пишется в `msg_err`.

### R4. Конвертеры потокобезопасны

Текущая реализация использует `static std::wstring_convert` — разделяемое изменяемое
состояние. Замена не должна содержать разделяемого состояния.

### R5. Одиночные методы чтения помечают неконвертируемое тело

`consume()` при невалидном UTF-8 в теле или ключе кладёт base64 и добавляет поле
`message_encoding` / `key_encoding` со значением `base64` — по образцу пакетных методов.

`getMessageData(Ложь)` при невалидном UTF-8 остаётся строкой (с U+FFFD по R1), но
факт подмены должен быть различим прикладным кодом: добавляется отдельный метод
`ДанныеСообщенияЯвляютсяТекстом` / `IsMessageDataText`, возвращающий, является ли
текущее тело валидным UTF-8. Штатный способ получить бинарь без потерь —
`ПолучитьДанныеСообщения(Истина)` — не меняется.

### R6. Значения заголовков читаются по паре (указатель, длина)

`consume()` и `getMessage()` используют `hdr.value_size()` вместо чтения до NUL.

## 3. Критерии приёмки

**AC1 — Битый UTF-8 в теле не роняет процесс**
Дано: consumer подписан на топик с сообщением, содержащим байт `0xFF` в теле.
Когда: 1С вызывает `ПрочитатьСообщение`, затем `ПолучитьДанныеСообщения(Ложь)`.
Тогда: метод возвращает строку, процесс сервера 1С не завершается, `std::terminate` не вызывается.

**AC2 — Бинарный доступ без потерь**
Дано: то же сообщение.
Когда: 1С вызывает `ПолучитьДанныеСообщения(Истина)`.
Тогда: возвращается двоичные данные, побайтово равные payload из Kafka.

**AC3 — `consume()` не роняет процесс**
Дано: то же сообщение.
Когда: 1С вызывает устаревший `ПрочитатьСообщения`/`consume`.
Тогда: возвращается корректный JSON, где `message` — base64, а `message_encoding` = `base64`.

**AC4 — Валидный UTF-8 не меняется**
Дано: сообщение с телом `{"текст":"привет"}` в UTF-8.
Когда: 1С вызывает `ПолучитьДанныеСообщения(Ложь)`.
Тогда: возвращается ровно исходная строка, без подстановки U+FFFD.

**AC5 — Двоичный заголовок не вызывает чтения за границей буфера**
Дано: сообщение с заголовком, значение которого содержит байт `0x00` в середине.
Когда: вызывается `ПрочитатьСообщение`.
Тогда: значение заголовка возвращается целиком по длине `value_size()`, санитайзер
адресов не фиксирует чтения за границей.

**AC6 — Исключение из конвертации не покидает компоненту**
Дано: метод компоненты, чей результат не удалось сконвертировать.
Когда: 1С вызывает этот метод.
Тогда: возвращается пустое значение, текст ошибки доступен через
`ПолучитьСообщениеОбОшибке`, процесс продолжает работу.

**AC7 — Признак текстовости тела**
Дано: сообщение с байтом `0xFF` в теле.
Когда: 1С вызывает `ДанныеСообщенияЯвляютсяТекстом`.
Тогда: возвращается `Ложь`. Для валидного UTF-8 тела — `Истина`.

## 4. Вне области

- Перекодировка CP1251 → UTF-8. Компонента не угадывает кодировку; несоответствие
  кодировки решается на стороне продюсера либо разбором двоичных данных в 1С.
- Изменение поведения Avro/Protobuf методов декодирования.
- Изменение поведения пакетных методов чтения — они уже соответствуют R5.
