# Спецификация: 64-битные смещения и причина отказа доставки

Статус: на утверждении
Дата: 2026-08-18
Основание: замечания по итогам миграции промышленной интеграции с 1.4.4 на 1.9.2 (пункты 2 и 5)

## 1. Проблемы

### 1.1. Смещение обрезается до 32 бит (пункт 2)

Kafka хранит смещение как int64, компонента внутри тоже держит его в `int64_t`
(`src/SimpleKafka1C.h:64`), но на границе с 1С оно повсеместно сужается до int32:

| Место | Код | Последствие |
|-------|-----|-------------|
| `src/consumer_methods.cpp:762` | `return (int32_t) this->offset;` | при смещении > 2 147 483 647 геттер отдаёт отрицательное или неверное число |
| `src/consumer_methods.cpp:958` | `std::int32_t tOffset = std::get<std::int32_t>(offset);` | фиксируется мусорное смещение; при передаче из 1С числа, не помещающегося в int32, — `bad_variant_access` |
| `src/consumer_methods.cpp:816` | `int64_t tOffset = static_cast<int64_t>(std::get<int32_t>(offset));` | то же для чтения по смещению |
| `src/consumer_methods.cpp:249` | `assignOffset = std::get<int32_t>(offset);` | то же для установки позиции чтения |

`УстановитьПозицииЧтения` (`src/consumer_methods.cpp:340`) уже разбирает смещение как
`long long` и в изменениях не нуждается.

Тихая часть проблемы — фиксация: `ЗафиксироватьСмещение` с обрезанным значением записывает
в Kafka позицию, которая после перезапуска даёт либо повторную обработку, либо пропуск
сообщений, и ни то ни другое не сопровождается ошибкой.

Уточнение к исходному замечанию: `bad_variant_access` **не** приводит к падению процесса —
`Component::CallAsFunc` и `Component::CallAsProc` (`src/Component.cpp:232`, `:257`) ловят
`std::exception` и `...`, кладут текст в `msg_err` и возвращают Ложь/0. То есть сейчас это
невнятное сообщение об ошибке, а не аварийное завершение rphost.

#### Ограничение платформы

Тип `variant_t` не поддерживает int64:

- вход: `Component::toStlVariant` (`src/Component.cpp:355-359`) обрабатывает `VTYPE_I4` (int32_t)
  и `VTYPE_R8` (double); ветка `VTYPE_I8` закомментирована. Число из 1С, не помещающееся в int32,
  приходит как `VTYPE_R8`, то есть double;
- выход: `Component::storeVariable` (`src/Component.cpp:386-393`) умеет отдавать только
  `VTYPE_I4` и `VTYPE_R8`.

Следовательно, единственный доступный способ передать смещение в обе стороны без потери
значимых разрядов — double. Double точно представляет целые до 2^53
(9 007 199 254 740 992), что на пять порядков превышает практически достижимые смещения Kafka
и полностью снимает исходную проблему. Расширять `variant_t` до `VTYPE_I8` в рамках этой
задачи не предлагается: это затрагивает базовый класс компоненты и все методы разом.

### 1.2. Текст ошибки продюсера не содержит причину отказа (пункт 5)

При отказе доставки `ПолучитьСообщениеОбОшибке` возвращает `"Not delivered. See log for details"`.
Причина при этом уже известна компоненте: `clDeliveryReportCb::dr_cb` кладёт
`"Delivery failed: " + message.errstr()` в общий слот асинхронных ошибок
(`src/SimpleKafka1C.cpp:246-248`).

Механика потери причины:

1. `produceAndWaitResult` (`src/producer_methods.cpp:261`) записывает в `msg_err` заглушку
   `"Not delivered. See log for details"`;
2. `getLastError` (`src/SimpleKafka1C.cpp:369`) отдаёт `msg_err` приоритетно и обращается
   к асинхронному слоту, только если `msg_err` пуст.

Заглушка перекрывает уже собранную причину. Второй путь потери — ветка
`outq_len() > 0` (`src/producer_methods.cpp:250`), где сообщение `"Messages not delivered: N"`
также не содержит кода ошибки.

Дополнительно: асинхронный слот очищается только в `initProducer`
(`src/producer_methods.cpp:76-81`) и `initConsumer` (`src/consumer_methods.cpp:26-31`).
Без очистки перед каждой отправкой с ожиданием результата ошибка от предыдущего сообщения
может быть показана как причина отказа текущего.

## 2. Границы задачи

В работу входит:

- перевод смещения на int64 на всех четырёх участках границы с 1С;
- новый хелпер конвертации `variant_t` в int64 с проверкой диапазона и типа;
- наполнение текста ошибки доставки причиной, кодом, топиком и партицией;
- очистка асинхронного слота перед отправкой с ожиданием результата;
- обновление `docs/consumer.md`, `docs/producer.md` и `CHANGELOG.md`.

В работу не входит (обсуждается отдельно):

- пункт 1 (временная метка в секундах) — правится следующей задачей;
- пункт 4 (метрики продюсера считают постановку в очередь);
- расширение `variant_t` до `VTYPE_I8`;
- унификация типов в выводе `Слушать` (пункт 3).

## 3. Функциональные требования

### FR-1. Хелпер конвертации

В `src/utils.h` / `src/utils.cpp` добавляется:

```cpp
// Converts a 1C-supplied number to int64. Accepts int32 and double
// (1C marshals values beyond int32 as VTYPE_R8). Rejects non-numbers,
// NaN/infinity, fractional values and magnitudes above 2^53, where
// double stops representing consecutive integers exactly.
bool variantToInt64(const variant_t& value, int64_t& out, std::string& errorMsg);
```

Правила:

| Вход | Результат |
|------|-----------|
| `int32_t` | принимается как есть |
| `double` без дробной части, \|v\| <= 2^53 | принимается |
| `double` с дробной частью | ошибка `"expected a whole number, got <v>"` |
| `double` NaN / бесконечность | ошибка `"expected a finite number"` |
| `double` \|v\| > 2^53 | ошибка `"number exceeds the exact integer range (2^53)"` |
| строка, булево, дата, двоичные данные, `Неопределено` | ошибка `"expected a number"` |

Хелпер не бросает исключений, текст ошибки пишется в `errorMsg`.
Поскольку `utils.h` сейчас не знает о `variant_t`, объявление размещается за
включением заголовка с определением типа (`Component.h`) либо `variant_t`
подключается в `utils.h` — конкретика на этапе плана.

### FR-2. `ПолучитьСмещениеСообщения` (`GetMessageOffset`)

Возвращаемый тип меняется с `int32_t` на `double`, значение отдаётся без сужения.
Со стороны 1С тип остаётся Числом, но теперь корректным при значениях выше 2^31.

### FR-3. `ЗафиксироватьСмещение` (`CommitOffset`)

Смещение принимается через `variantToInt64`. Дополнительно:

- партиция проверяется через `std::holds_alternative<int32_t>` (сейчас — прямой `std::get`);
- имя топика проверяется на тип и через `isValidTopicName`;
- отрицательное смещение отвергается с текстом `"Offset must be >= 0"` — специальные позиции
  задаются методами `ПерейтиКНачалу` / `ПерейтиККонцу` / `ПерейтиКВременнойМетке`,
  а не фиксацией;
- при ошибке типа метод возвращает Ложь и внятный текст в `ПолучитьСообщениеОбОшибке`,
  а не `bad variant access`.

### FR-4. `ПрочитатьСообщениеПоСмещению` (`ReadMessageByOffset`)

Смещение принимается через `variantToInt64`, отрицательные значения отвергаются.
Прочие параметры получают проверку типа вместо прямого `std::get`.

### FR-5. `УстановитьПозициюЧтения` (`SetReadingPosition`)

`assignOffset` становится `int64_t` и заполняется через `variantToInt64`.
Существующая проверка через `checkReadingPosition` уже принимает `int64_t`
(`src/consumer_methods.cpp:156`) и не меняется.

Уточнение, внесённое при реализации: отрицательные смещения здесь **не отвергаются**.
`checkReadingPosition` (`src/consumer_methods.cpp:213-215`) намеренно пропускает их как
специальные смещения librdkafka (`-1` — конец, `-2` — начало, `-1000` — сохранённое),
и запрет сломал бы работающий сценарий. Проверка «смещение >= 0» действует только
в `ЗафиксироватьСмещение` (FR-3) и `ПрочитатьСообщениеПоСмещению` (FR-4), где специальные
значения смысла не имеют.

### FR-6. Текст ошибки доставки

`clDeliveryReportCb::dr_cb` формирует сообщение вида:

```
Delivery failed: Broker: Topic authorization failed (topic=my-topic, partition=2, code=29)
```

где текст — `message.errstr()`, код — числовое значение `message.err()`,
топик — `message.topic_name()`, партиция — `message.partition()`.

### FR-7. Причина в результате отправки с ожиданием

`produceAndWaitResult`:

- перед вызовом `produceFn()` очищает `asyncErrorState->lastError`, чтобы причина
  от предыдущей отправки не выдавалась за причину текущей;
- в ветке `outq_len() > 0` и в ветке «доставка не подтверждена» подставляет в `msg_err`
  текст из асинхронного слота, если он непуст;
- если слот пуст (delivery report не пришёл), сохраняется прежняя формулировка
  с явным указанием, что подробностей нет:
  `"Not delivered: no delivery report received"` и
  `"Messages not delivered: N (no delivery report received)"`.

Поведение возвращаемого числового вердикта (`2` — доставлено, `0` — нет, `-1` — ошибка
постановки в очередь) не меняется.

## 4. Критерии приёмки

**AC-1.** Дано: топик со смещением 3 000 000 000. Когда 1С читает сообщение через
`ПрочитатьСообщение` и вызывает `ПолучитьСмещениеСообщения`. Тогда возвращается 3000000000,
а не отрицательное число.

**AC-2.** Дано: инициализированный консьюмер. Когда 1С вызывает
`ЗафиксироватьСмещение("topic", 3000000000, 0)`. Тогда в Kafka фиксируется смещение
3000000000, метод возвращает Истина.

**AC-3.** Дано: инициализированный консьюмер. Когда 1С вызывает
`ЗафиксироватьСмещение("topic", "abc", 0)`. Тогда метод возвращает Ложь, а
`ПолучитьСообщениеОбОшибке` содержит `expected a number`, но не `bad variant access`.

**AC-4.** Дано: инициализированный консьюмер. Когда 1С вызывает
`ЗафиксироватьСмещение("topic", 100.5, 0)`. Тогда метод возвращает Ложь с текстом
`expected a whole number`.

**AC-5.** Дано: инициализированный консьюмер. Когда 1С вызывает
`ЗафиксироватьСмещение("topic", -5, 0)`. Тогда метод возвращает Ложь с текстом
`Offset must be >= 0`.

**AC-6.** Дано: смещение 1500 (значение, помещающееся в int32). Когда выполняются
`ЗафиксироватьСмещение`, `ПрочитатьСообщениеПоСмещению` и `УстановитьПозициюЧтения`
с прежним кодом 1С без изменений. Тогда поведение совпадает с 1.9.3 —
обратная совместимость по существующим сценариям сохранена.

**AC-7.** Дано: топик, запрещённый ACL для текущего пользователя. Когда 1С вызывает
`ОтправитьСообщениеСОжиданиемРезультата`. Тогда метод возвращает 0, а
`ПолучитьСообщениеОбОшибке` содержит причину, топик и партицию, например
`Delivery failed: Broker: Topic authorization failed (topic=denied-topic, partition=-1, code=29)`.

**AC-8.** Дано: предыдущая отправка завершилась отказом, ошибка осталась в асинхронном слоте.
Когда следующая отправка в разрешённый топик проходит успешно. Тогда метод возвращает 2,
а `ПолучитьСообщениеОбОшибке` не содержит текста прошлой ошибки.

**AC-9.** Дано: продюсер и брокер, где delivery report не приходит до истечения flush-таймаута.
Когда вызывается `ОтправитьСообщениеСОжиданиемРезультата`. Тогда текст ошибки явно сообщает
об отсутствии delivery report, а не о конкретной причине отказа.

**AC-10.** Сборка `cmake --build out/build/x64-Release --config Release` проходит без ошибок
и без новых предупреждений компилятора.

## 5. Совместимость и версия

- FR-2 меняет тип возвращаемого значения `ПолучитьСмещениеСообщения` с `VTYPE_I4` на `VTYPE_R8`.
  Для кода 1С это остаётся Числом; ломается только код, полагающийся на целочисленное
  представление на уровне внешнего API (например, сравнение типов), чего в 1С нет.
- FR-3 добавляет отказ на отрицательное смещение — ранее такой вызов уходил в Kafka.
- Версия **не поднимается**: остаётся `1.9.3` (`src/SimpleKafka1C.h:31`). Бинарного релиза
  1.9.3 ещё не было, поэтому изменения входят в состав того же, ещё не опубликованного
  выпуска, а не образуют новый. Записи добавляются в существующий раздел `## [1.9.3]`
  файла `CHANGELOG.md`.

## 6. Открытые вопросы

1. **Смещения выше 2^53.** Практически недостижимы, но формально хелпер их отвергнет,
   а геттер потеряет точность. Добавлять ли строковый вариант геттера
   (`ПолучитьСмещениеСообщенияСтрокой`) или ограничиться записью в документации?
   Предложение: ограничиться документацией.
2. **Проверка.** Автотестов в репозитории нет. Проверка планируется сборкой и ручным
   сценарием на брокере с SASL и ACL. Нужен ли минимальный отдельный тест на
   `variantToInt64` (потребует новой цели в CMake)?
   Предложение: не добавлять в рамках этой задачи.
3. ~~Версия~~ — решено: версия не поднимается, правки входят в неопубликованную 1.9.3
   (см. раздел 5).

## 7. План реализации

Утверждён: спецификация, оба открытых вопроса по варианту «по умолчанию» (строковый геттер
не добавляем, отдельный тест на `variantToInt64` не заводим), версия остаётся 1.9.3.

Каждый шаг — минимальный набор файлов, после каждого шага сборка
`cmake --build out/build/x64-Release --config Release` из окружения VS.
Если DLL держит rphost и линковка падает с `LNK1104`, старая DLL переименовывается
перед сборкой и удаляется после.

### Шаг 1. Хелпер `variantToInt64`

Файлы: `src/utils.h`, `src/utils.cpp`.

`variant_t` объявлен в `src/Component.h:43-52`, поэтому `utils.h` получает `#include "Component.h"`.
Заголовок уже входит в цепочку включений всех `.cpp`, где будет использоваться хелпер,
циклов не возникает: `Component.h` не включает `utils.h`.

Реализация — по таблице FR-1: `int32_t` пропускается как есть; `double` проверяется
`std::isfinite`, на целость (`std::trunc(v) == v`) и на диапазон `2^53`; остальные
альтернативы варианта дают ошибку `"expected a number"`. Возврат `false` + текст в `errorMsg`,
исключения не бросаются.

### Шаг 2. Геттер смещения (FR-2)

Файлы: `src/SimpleKafka1C.h` (объявление), `src/consumer_methods.cpp:761`.

Тип меняется `int32_t` → `double`, тело — `return static_cast<double>(this->offset);`.
Регистрация в `AddMethod` (`src/SimpleKafka1C.cpp:445`) не меняется: тип выводится из сигнатуры,
а `Component::storeVariable` отдаёт `double` как `VTYPE_R8`.

### Шаг 3. `ЗафиксироватьСмещение` (FR-3)

Файл: `src/consumer_methods.cpp:955-978`.

Порядок проверок: тип топика → `isValidTopicName` → тип партиции (`holds_alternative<int32_t>`,
значение >= 0) → `variantToInt64` для смещения → смещение >= 0. Далее существующая логика
`TopicPartition::create` (принимает `int64_t`) без изменений.

### Шаг 4. Чтение по смещению и позиция чтения (FR-4, FR-5)

Файл: `src/consumer_methods.cpp:809-820` и `:240-256`.

В `readMessageByOffset` прямые `std::get` заменяются проверками типов, смещение идёт через
`variantToInt64`, отрицательное отвергается. В `setReadingPosition` `assignOffset` становится
`int64_t`, заполняется тем же хелпером; блок `try/catch` вокруг `std::get` для топика и партиции
сохраняется. `checkReadingPosition` уже принимает `int64_t` (`:156`) — не трогается.
`setReadingPositions` не трогается: там уже `long long`.

### Шаг 5. Текст delivery report (FR-6)

Файл: `src/SimpleKafka1C.cpp:242-248`.

В блок заполнения `asyncError->lastError` добавляются код, топик и партиция:
`"Delivery failed: " + errstr + " (topic=" + topic_name + ", partition=" + partition + ", code=" + err + ")"`.
Блок уже под `std::lock_guard`, потокобезопасность не меняется.

### Шаг 6. Причина в синхронной отправке (FR-7)

Файл: `src/producer_methods.cpp:244-266`.

Перед `produceFn()` — очистка `asyncErrorState->lastError` под мьютексом (по образцу
`initProducer`, `src/producer_methods.cpp:76-81`). В обеих ветках отказа причина берётся
из слота, при пустом слоте используются формулировки из FR-7. Вердикт и запись в лог-файл
сохраняются как есть.

### Шаг 7. Документация

Файлы: `docs/consumer.md`, `docs/producer.md`.

- `ПолучитьСмещениеСообщения` (`consumer.md:429`) — смещение 64-битное, оговорка про предел
  точности 2^53;
- `ЗафиксироватьСмещение` (`:615`) — принимаемые значения, требование >= 0, отсылка к
  `ПерейтиКНачалу` / `ПерейтиККонцу` для специальных позиций, тексты ошибок;
- `ПрочитатьСообщениеПоСмещению` (`:633`) и `УстановитьПозициюЧтения` (`:105`) — то же по смещению;
- `producer.md`, раздел синхронной отправки (`:293-330`) — новый вид текста ошибки с причиной,
  топиком, партицией и кодом, плюс пример разбора на 1С.

### Шаг 8. CHANGELOG

Файл: `CHANGELOG.md`, существующий раздел `## [1.9.3]`, подраздел `### Исправлено`
— две записи: сужение смещения до 32 бит и потеря причины отказа доставки.

### Порядок и проверка

Шаги 1-4 (смещения) и 5-6 (ошибка доставки) независимы между собой, но выполняются
последовательно, чтобы каждая сборка проверяла один смысловой блок. Итоговая проверка —
критерии AC-1…AC-10 раздела 4; AC-1, AC-2, AC-7, AC-8 требуют живого брокера и выполняются
на стороне интегратора, остальные проверяются локально.

### Замечание вне задачи

В `Component::AddMethod` (`src/Component.h:198-202`) флаги `returns_bool` и `returns_int32_t`
заполняются отрицаниями (`!std::is_same<T, bool>`), из-за чего ветка подстановки значения
при исключении в `CallAsFunc` (`src/Component.cpp:268-272`) выбирает неверный тип: метод,
возвращающий Булево, при исключении отдаёт `-1`, а не `Ложь`. На эту задачу не влияет
(смена `int32_t` на `double` в шаге 2 флаги не меняет, а геттер смещения исключений не бросает),
