# Спецификация: чтение очередью (share consumer, KIP-932)

Статус: спецификация и план утверждены 2026-10-14; все шаги 1–9 выполнены 2026-10-15
Дата: 2026-10-14
Версия компоненты: 1.10.0, librdkafka 2.16.0

## 1. Цель

Дать 1С возможность читать топик **очередью** — через share group (KIP-932, Queues for Kafka).
В отличие от consumer group:

- одну партицию одновременно читают несколько членов группы, поэтому число обработчиков
  (фоновых заданий 1С) не ограничено числом партиций;
- прогресс учитывается по каждой записи, а не по офсету партиции: запись можно подтвердить
  (`accept`), вернуть в очередь для повторной доставки (`release`) или отклонить навсегда
  (`reject`);
- с каждой записью приходит номер доставки (`delivery_count`).

Целевой кейс в 1С: пул фоновых заданий разбирает независимые задания (заявки, платежи,
уведомления). Неудачная запись возвращается в очередь и не останавливает остальные,
«отравленная» запись отклоняется после N попыток. Собственный регистр-очередь
и регламентное задание повторов не нужны.

Не цель: порядок обработки, exactly-once, перечитывание по офсету.

## 2. Ограничения librdkafka и брокера

Источник: `rdkafka.h` (librdkafka 2.15.1; в 2.16.0 раздел не менялся), раздел «Share consumer (Queues for Kafka)».

1. **Preview.** Публичный API может измениться до GA, производитель не рекомендует его для
   продакшена. Новые методы помечаются в документации как экспериментальные.
2. **Только C API** (`rd_kafka_share_t`), C++-обёртки нет. Существующие методы, работающие
   с `RdKafka::KafkaConsumer` / `RdKafka::Message`, к share consumer не применяются.
3. **Брокер Apache Kafka ≥ 4.2** с включёнными share groups.
4. **Handle не потокобезопасен.** Параллельный вызов librdkafka отклоняет с
   `RD_KAFKA_RESP_ERR__CONFLICT`. Механизма wakeup нет: `poll` завершается только по таймауту.
5. **Блокировка записи** выдаётся на `group.share.record.lock.duration.ms` (по умолчанию 30 с,
   настройка брокера или группы, не клиента). Продлить её нельзя (RENEW не реализован). Если
   запись не подтверждена вовремя, её доставят повторно, возможно другому члену группы.
6. **Лимит доставок** задаёт брокер: `group.share.delivery.count.limit`, по умолчанию 5.
   После него запись архивируется и больше не доставляется.
7. Нет seek, подписки по regex, admin-операций для share groups и автосоздания топиков.
   `max.poll.records` ограничивает пакет нестрого.
8. Порядок обработки записей не гарантируется.
9. Не применяются к share consumer: `enable.auto.commit`, `isolation.level`,
   `partition.assignment.strategy`, `enable.partition.eof`. Единственная клиентская настройка
   share — `share.acknowledgement.mode`.

## 3. Новые методы

Все методы — экспериментальные. Обычный consumer (`ИнициализироватьКонсьюмера` и связанные
методы) не меняется. Share consumer и обычный consumer — независимые экземпляры, в одном
объекте компоненты могут существовать одновременно.

| Английское имя | Русское имя | Параметры | Возврат |
|---|---|---|---|
| `InitializeShareConsumer` | `ИнициализироватьКонсьюмераОчереди` | `Брокеры` (Строка), `ИмяГруппы` (Строка) | Булево |
| `ShareSubscribe` | `ПодписатьсяНаОчередь` | `Топики` (Строка, имена через запятую) | Булево |
| `ShareUnsubscribe` | `ОтписатьсяОтОчереди` | — | Булево |
| `ShareReadBatch` | `ПрочитатьПакетИзОчереди` | `МаксОжиданиеМс` (Число, по умолчанию 1000), `КакBase64` (Булево, по умолчанию Ложь), `ВернутьНеподтвержденные` (Булево, по умолчанию Ложь) | Строка (JSON) |
| `ShareAcknowledge` | `ПодтвердитьСообщениеОчереди` | `Топик` (Строка), `Раздел` (Число), `Смещение` (Строка или Число), `Решение` (Строка: `accept`, `release`, `reject`) | Булево |
| `ShareAcknowledgeBatch` | `ПодтвердитьСообщенияОчереди` | `Подтверждения` (Строка, JSON-массив, см. 4.4) | Булево |
| `ShareCommit` | `ЗафиксироватьПодтвержденияОчереди` | `ТаймаутМс` (Число, по умолчанию 5000) | Булево |
| `StopShareConsumer` | `ОстановитьКонсьюмераОчереди` | — | Булево |

Порядок работы в 1С: `УстановитьПараметр` (необязательно) → `ИнициализироватьКонсьюмераОчереди` →
`ПодписатьсяНаОчередь` → цикл { `ПрочитатьПакетИзОчереди` → обработка →
`ПодтвердитьСообщениеОчереди` по каждой записи } → `ОстановитьКонсьюмераОчереди`.

При ошибке методы возвращают Ложь или пустую строку, текст ошибки доступен через
`ПолучитьСообщениеОбОшибке`.

## 4. Поведение

### 4.1. Инициализация

- Режим подтверждения всегда **явный** (`share.acknowledgement.mode=explicit`): в этом смысл
  очереди для 1С. Если пользователь задал `share.acknowledgement.mode` через `УстановитьПараметр`,
  значение заменяется на `explicit`. Неявного режима нет (решение 9.1).
- Настройки из `УстановитьПараметр` применяются так же, как для Admin API (C-перегрузка
  `applyKafkaSettings`), включая перехват `openssl.*` и `applyOpenSSLConfig()`.
- Настройки, которые `rd_kafka_share_consumer_new` отвергает (иначе клиент не создаётся),
  компонента пропускает и пишет в лог `[share] ignored property <ключ>`. Список по исходникам
  librdkafka 2.16.0 (`rdkafka_conf.c`) и проверке на стенде: `enable.auto.commit`,
  `auto.offset.reset`, `isolation.level`, `enable.partition.eof`,
  `partition.assignment.strategy`, `group.protocol`, `group.protocol.type`,
  `group.remote.assignor`, `group.instance.id`, `session.timeout.ms`,
  `heartbeat.interval.ms`, `socket.max.fails`, `queued.min.messages`,
  `queued.max.messages.kbytes`, `fetch.queue.backoff.ms`, `fetch.error.backoff.ms`,
  `message.copy.max.bytes`, `topic.blacklist`, `allow.auto.create.topics`,
  `consume.callback.max.messages`. Так одни и те же настройки можно использовать
  для обычного consumer и для очереди.
- `ИмяГруппы` пустое → ошибка, клиент не создаётся.
- Повторная инициализация сначала закрывает предыдущий share consumer, как при
  `ОстановитьКонсьюмераОчереди`.

### 4.2. Подписка

- Принимаются только точные имена топиков. Пустой список → ошибка.
- Повторный вызов заменяет подписку.

### 4.3. Чтение пакета

Возвращается JSON в формате `ЧитатьПакетСообщений`, в каждую запись добавляется поле
`delivery_count`:

```json
{"messages":[{"message":"...","key":"...","topic":"orders","partition":0,"offset":42,
  "broker_id":1,"timestamp":1760000000000,"headers":[...],"delivery_count":1}],"count":1}
```

- Таймаут без сообщений → `{"messages":[],"count":0}`, без ошибки.
- Ошибка уровня записи (librdkafka возвращает сообщение с ненулевым `err`): запись попадает
  в массив с полем `"error"` (текст librdkafka) и без данных. Топик, раздел и смещение
  заполнены. Подтверждать такую запись не нужно: librdkafka сама помечает её `reject`
  (битый CRC, неподдерживаемый формат) или `release` (ошибка распаковки) и не считает
  неподтверждённой. Попытка подтвердить её → ошибка
  `"Record has error and is acknowledged automatically"`.
- Ошибка уровня вызова → пустая строка, текст в `ПолучитьСообщениеОбОшибке`.
- Если в предыдущем пакете остались неподтверждённые записи:
  - `ВернутьНеподтвержденные = Ложь` → метод возвращает пустую строку и ошибку
    `"Previous batch has unacknowledged records"`, к брокеру не обращается;
  - `ВернутьНеподтвержденные = Истина` → всем неподтверждённым записям прошлого пакета
    ставится `release`, затем выполняется чтение. Так обработчик 1С восстанавливается
    после исключения без перезапуска консьюмера.
- Компонента держит последний пакет до следующего чтения или остановки, чтобы подтверждать
  записи по топику, разделу и смещению.

### 4.4. Подтверждение

- `Решение`: регистр не важен. Допустимы `accept`, `release`, `reject`, иначе ошибка.
- `Смещение` принимается Строкой или Числом. Строка — основной способ: Число больше int32
  обрезается платформой (#91).
- Запись, которой нет в последнем пакете → ошибка `"Record not found in current batch"`,
  в Kafka ничего не отправляется.
- Повторное подтверждение уже подтверждённой записи → ошибка `"Record is already acknowledged"`. librdkafka сама его не
  отвергает: до фиксации побеждает последнее решение (проверено на стенде), поэтому статус
  подтверждения ведёт компонента.
- Подтверждение только отмечает запись. Брокер получает его при следующем
  `ПрочитатьПакетИзОчереди`, `ЗафиксироватьПодтвержденияОчереди` или `ОстановитьКонсьюмераОчереди`.
- `ПодтвердитьСообщенияОчереди` принимает массив
  `[{"topic":"orders","partition":0,"offset":"42","ack":"accept"}, ...]`. Обрабатывает все
  элементы. Если хотя бы один не прошёл, возвращает Ложь и перечисляет ошибочные элементы
  в тексте ошибки; успешные остаются подтверждёнными.

### 4.5. Фиксация

`ЗафиксироватьПодтвержденияОчереди` синхронно отправляет накопленные подтверждения
(`rd_kafka_share_commit_sync`). Если по какому-то разделу пришла ошибка, метод возвращает
Ложь, а текст ошибки содержит топик, раздел и ошибку по каждому такому разделу. Автоматического
повтора нет (так ведёт себя librdkafka). Нет ожидающих подтверждений → Истина.

### 4.6. Остановка

`ОстановитьКонсьюмераОчереди` вызывает `rd_kafka_share_consumer_close` (отправляет
подтверждённое, выходит из группы, время ограничено примерно `socket.timeout.ms`), затем
`rd_kafka_share_destroy`. Неподтверждённые записи возвращаются в очередь по истечении
блокировки. Деструктор компоненты делает то же.

### 4.7. Потоки

Все вызовы share consumer сериализуются мьютексом компоненты. Фонового потока в этой версии
нет (push-режим для очереди — вне объёма, раздел 7).

### 4.8. Логирование

Ошибки и события пишутся в лог консьюмера, если он включён, с префиксом `[share]`.

## 6. Критерии приёмки

Стенд: Apache Kafka ≥ 4.2 с включёнными share groups, топик `q-test` с 1 партицией (если
не сказано иное), группа `sg-test`.

**AC-1. Инициализация и подписка**
Given брокер доступен
When вызвать `ИнициализироватьКонсьюмераОчереди(Брокеры, "sg-test")` и `ПодписатьсяНаОчередь("q-test")`
Then оба метода возвращают Истина.

**AC-2. Пустая группа**
Given любое состояние
When вызвать `ИнициализироватьКонсьюмераОчереди(Брокеры, "")`
Then возврат Ложь, ошибка сообщает, что имя группы обязательно.

**AC-3. Чтение пакета**
Given в `q-test` записаны 10 сообщений
When вызвать `ПрочитатьПакетИзОчереди(5000)`
Then JSON содержит записи с полями формата `ЧитатьПакетСообщений` и `delivery_count = 1`.

**AC-4. Accept**
Given прочитан пакет
When подтвердить все записи `accept`, затем `ЗафиксироватьПодтвержденияОчереди()`
Then возврат Истина, а после переподключения этой группы те же записи не доставляются.

**AC-5. Release и повторная доставка**
Given прочитана запись со смещением N
When подтвердить её `release` и снова вызвать `ПрочитатьПакетИзОчереди`
Then запись N приходит снова с `delivery_count = 2`.

**AC-6. Reject**
Given прочитана запись N
When подтвердить её `reject` и прочитать снова
Then запись N больше не доставляется.

**AC-7. Несколько читателей одной партиции**
Given в `q-test` (1 партиция) 100 сообщений, запущены 2 экземпляра компоненты в одной группе
When оба читают в цикле с подтверждением `accept`
Then оба экземпляра получают записи, сумма уникальных смещений равна 100.

**AC-8. Неподтверждённый пакет**
Given прочитан пакет, одна запись не подтверждена
When вызвать `ПрочитатьПакетИзОчереди`
Then возврат пустая строка, ошибка `"Previous batch has unacknowledged records"`.

**AC-8a. Возврат неподтверждённых**
Given прочитан пакет, запись N не подтверждена
When вызвать `ПрочитатьПакетИзОчереди(5000, Ложь, Истина)`
Then чтение успешно, запись N приходит снова с `delivery_count = 2`.

**AC-9. Истечение блокировки**
Given экземпляр A прочитал запись N и не подтверждает её
When прошло больше `group.share.record.lock.duration.ms`, экземпляр B читает
Then B получает запись N с `delivery_count = 2`.

**AC-10. Чужая запись**
Given прочитан пакет без смещения 999
When вызвать `ПодтвердитьСообщениеОчереди("q-test", 0, "999", "accept")`
Then возврат Ложь, ошибка `"Record not found in current batch"`.

**AC-11. Неверное решение**
When вызвать `ПодтвердитьСообщениеОчереди(..., "commit")`
Then возврат Ложь, ошибка перечисляет допустимые значения.

**AC-12. Смещение больше int32**
Given запись со смещением > 2147483647 в текущем пакете
When подтвердить её, передав смещение Строкой
Then возврат Истина.

**AC-13. Пакетное подтверждение**
Given прочитан пакет из 3 записей
When передать в `ПодтвердитьСообщенияОчереди` массив, где 2 элемента верные и 1 с чужим смещением
Then возврат Ложь, в ошибке указан один ошибочный элемент, а 2 записи подтверждены (AC-4 для них выполняется).

**AC-14. Остановка**
Given записи подтверждены, но не зафиксированы
When вызвать `ОстановитьКонсьюмераОчереди()`
Then возврат Истина, подтверждения дошли до брокера (записи не доставляются повторно).

**AC-15. Брокер без share groups**
Given брокер Kafka < 4.2 или share groups выключены
When инициализировать, подписаться и читать
Then метод чтения возвращает пустую строку с понятным текстом ошибки, компонента не падает.

**AC-16. Независимость от обычного consumer**
Given запущены обычный consumer и share consumer в одном объекте компоненты
When работать с обоими
Then оба работают, остановка одного не влияет на другой.

**AC-17. Сборка и версия librdkafka**
Given изменения внесены
When собрать Windows x64 и Linux (WSL Ubuntu 24.04)
Then сборки проходят без новых предупреждений, а в логе консьюмера
строка librdkafka — `2.16.0` (проверка `rd_kafka_version_str()` в рантайме, не по заголовку).

**AC-18. Регрессия обычного consumer и producer на 2.16.0**
Given компонента собрана с librdkafka 2.16.0
When на стенде отправить и прочитать сообщения обычными методами (`ОтправитьСообщение`,
`ЧитатьПакетСообщений`, `ЗафиксироватьСмещение`)
Then поведение прежнее.

## 7. Вне объёма

- Push-режим (фоновое чтение через ExternalEvent) для очереди — отдельная спека после проверки
  синхронного варианта.
- Admin-операции share groups (список, описание, удаление, lag) — в librdkafka их нет.
- Методы `ПолучитьДанныеСообщения` и другие геттеры «текущего сообщения» для очереди — данные
  только в JSON пакета.
- Декодирование Avro и Protobuf — уже делается отдельными методами по данным из JSON.

## 8. Риски

- API Preview может измениться в следующей версии librdkafka: вплоть до несовместимости при
  обновлении vcpkg.
- Комментарий в `rdkafka.h` к `rd_kafka_share_acknowledge_offset` («TODO KIP-932: Check if it
  should only be allowed for error cases like Java») — функцию могут ограничить. Поэтому
  подтверждение реализуется через удерживаемый пакет и `rd_kafka_share_acknowledge_type`.
  В 2.16.0 обе функции вызывают одну внутреннюю `rd_kafka_share_acknowledge_offset0`.
- У пользователей мало кластеров 4.2+: функцию смогут проверить немногие.
- Порта librdkafka 2.16.0 в vcpkg ещё нет (там 2.15.1). Нужен overlay-порт; в WSL github
  недоступен — исходники скачиваются на Windows и подкладываются в `downloads`.
- В WSL сейчас стоит librdkafka 2.12.1: Linux-сборка поднимается сразу на 4 минорных версии.

## 9. Решения (2026-10-14)

1. Только `explicit`.
2. Подтверждение записей с ошибкой не нужно: librdkafka помечает их сама (шаг 3, по
   исходникам `rdkafka_msgset_reader.c`, `rdkafka_fetcher.c`).
3. `ВернутьНеподтвержденные` — добавить.
4. Версия компоненты 1.10.0; внутри — librdkafka 2.16.0 (Windows и Linux).
5. Стенд Kafka поднимается в Docker.

## 10. План реализации

Каждый шаг — минимум файлов, после шага сборка (Windows) и проверка по указанным AC.

### Шаг 1. Стенд Kafka 4.2 в Docker — выполнен 2026-10-14

Итог: `apache/kafka:4.2.2`, `share.version=1` включён по умолчанию, блокировка 15 с.
Новая share group стартует с `latest` — для `sg-test` выставлен `earliest`.
Консольный share consumer читает записанные сообщения.
