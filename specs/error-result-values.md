# Спецификация: значение функции при необработанном исключении соответствует её типу

Статус: реализовано 2026-10-28 (1.10.2), не закоммичено
Связанные изменения: issue #95 (asosnoviy), включая комментарий о строковых и числовых методах

## 1. Проблема

`docs/exceptionHandling.md` обещает: если в функции компоненты возникла исключительная ситуация,
выполнение модуля 1С не прерывается, а функция возвращает значение, по которому ошибку можно
распознать: `Ложь` для булева, `-1` для целого, пустое значение для остальных типов. Текст ошибки
доступен через `ПолучитьСообщениеОбОшибке()`.

Фактически обещание не выполняется. Исключение, которое метод не перехватил сам, ловит
`Component::CallAsFunc` (`src/Component.cpp`). Обычно это `std::bad_variant_access`: метод
вызвал `std::get<...>` до своего `try`, а 1С передала аргумент другого типа. Диспетчер выбирает
значение ошибки по признакам `returns_bool` и `returns_int32_t` из `MethodMeta`.

1. **Признаки вычислены с обратным знаком.** В `Component::AddMethod` (`src/Component.h`) стоит
   `!std::is_same<T, bool>::value` и `!std::is_same<T, int32_t>::value`. Дефект появился в
   `ca1cc03`. Последствия:

   | Тип возврата | Ожидается | Фактически |
   |---|---|---|
   | `bool` | `Ложь` | `-1` |
   | `int32_t` | `-1` | `Ложь` |
   | `std::string`, `double`, `variant_t` | пустое значение | `Ложь` |

   Самый опасный случай — булев метод. `-1` в условии `Если Результат Тогда` даёт `Истина`:
   метод упал, а код 1С идёт по ветке успеха. Для целых методов не срабатывает принятая
   проверка `Если Результат = -1 Тогда`.

2. **Для строки и числа нет своего значения ошибки.** Даже с правильными признаками у методов
   `std::string` и `double` переменная `result` остаётся `std::monostate`, и в 1С приходит
   `Неопределено`. Для числа это хуже всего: арифметика или сравнение с `Неопределено`
   вызывает ошибку времени выполнения, и модуль 1С прерывается.

3. **Текст ошибки начинается с пробела.** Обработчик делает `msg_err += " "` и только потом
   дописывает `e.what()`, хотя `msg_err` перед вызовом уже очищен. Получается
   « std::get: wrong index for variant».

## 2. Решение

### 2.1. Признаки типа

- В `Component::AddMethod` убрать `!` у `returns_bool` и `returns_int32_t`.
- В `Component::MethodMeta` добавить признаки `returns_string` (`T` — `std::string`) и
  `returns_double` (`T` — `double`).

### 2.2. Значение ошибки в `Component::CallAsFunc`

| Тип возврата | Значение при исключении |
|---|---|
| `bool` | `false` |
| `int32_t` | `-1` |
| `std::string` | пустая строка |
| `double` | `-1.0` |
| `variant_t` | без изменений: `Неопределено` |

**Число возвращает `-1`, а не `0`, как предложено в комментарии к issue.** Причины:

- единственный затронутый метод `ПолучитьКоличествоСообщенийВПартиции` при своих ошибках
  уже возвращает `-1.0` (`src/admin_metadata.cpp`), и `docs/admin.md` так и описывает;
- `0` — нормальный результат (пустая партиция, смещение 0), отличить его от ошибки нельзя;
- поведение совпадает с целыми методами.

Тип значения метода `variant_t` заранее неизвестен, поэтому подставлять пустую строку или
число наугад нельзя: `Неопределено` остаётся.

### 2.3. Текст ошибки

В обоих `catch` в `CallAsFunc` присваивать текст: `msg_err = e.what();` и
`msg_err = UNKNOWN_EXCP;`, как уже сделано в `CallAsProc`.

### 2.4. Документация и версия

- `docs/exceptionHandling.md`: добавить «для типа число — значение **-1**», уточнить, что
  `Неопределено` возвращают методы с произвольным типом результата. Исправить опечатку
  «Предпрятие».
- `CHANGELOG.md`: раздел «Исправлено» в новой версии.
- Версия: `1.10.2`, потому что тег `v1.10.1` уже опубликован в origin (см. раздел 5).

## 3. Область изменений

В объём входят: `src/Component.h`, `src/Component.cpp`, `docs/exceptionHandling.md`,
`CHANGELOG.md`, `src/SimpleKafka1C.h` (версия) и регрессионная проверка (раздел 4.2).

В объём **не** входит:

- перенос `std::get<...>` внутрь `try` в отдельных методах. После исправления диспетчер и так
  возвращает правильное значение, а такая правка затрагивает около 70 методов;
- изменение значений ошибки, которые методы возвращают сами из своих `catch`;
- сборка и публикация релиза.

## 4. Критерии приёмки

### 4.1. Поведение

**AC-1. Булев метод**
- Given компонента подключена
- When вызывается `УстановитьТаймаутОжидания("не число")`
- Then результат имеет тип `Булево` и равен `Ложь`
- And `ПолучитьСообщениеОбОшибке()` возвращает непустой текст.

**AC-2. Целый метод**
- Given компонента подключена и продюсер инициализирован (`ИнициализироватьПродюсера`)
- When вызывается `ОтправитьПакетСообщений("[]", 123)`: имя топика передано числом
- Then результат имеет тип `Число` и равен `-1`.

Продюсер нужен, потому что все методы `int32_t` сначала проверяют `hProducer` и без него
возвращают `-1` сами, не доходя до `std::get<...>`.

**AC-3. Строковый метод**
- Given компонента подключена
- When вызывается `ПолучитьСписокТопиков(123)`
- Then результат имеет тип `Строка` и `ПустаяСтрока(Результат)` равно `Истина`.

**AC-4. Числовой метод (double)**
- Given компонента подключена
- When вызывается `ПолучитьКоличествоСообщенийВПартиции(123, "topic", 0)`
- Then результат имеет тип `Число` и равен `-1`
- And выражение `Результат + 1` выполняется без ошибки времени выполнения.

**AC-5. Метод с произвольным типом результата**
- Given компонента подключена
- When вызывается `ПолучитьДанныеСообщения("не булево")`
- Then результат равен `Неопределено`.

**AC-6. Текст ошибки**
- Given функция завершилась исключением, которое поймал диспетчер
- When вызывается `ПолучитьСообщениеОбОшибке()`
- Then текст совпадает с `what()` исключения и не начинается с пробела.

**AC-7. Успешный вызов не изменился**
- Given аргументы верного типа
- When вызывается любой из методов AC-1–AC-5
- Then результат совпадает с результатом до исправления.

### 4.2. Проверка

- Сборка Windows (`x64-Release`) проходит без новых предупреждений.
- AC-1–AC-6 проверяются тестом, который загружает собранную DLL через Native API, как платформа,
  и смотрит тип и значение `tVariant` (`VTYPE_BOOL`, `VTYPE_I4`, `VTYPE_PWSTR`, `VTYPE_R8`,
  `VTYPE_EMPTY`). Живой брокер не нужен: исключение возникает до обращения к Kafka. Для AC-2
  продюсер инициализируется с недоступным адресом брокера; если librdkafka откажет в создании
  продюсера без брокера, AC-2 проверяется на Docker-стенде.
- AC-7 проверяется тем же тестом на методах без брокера (`УстановитьТаймаутОжидания(1000)`).

## 5. Решения

1. **Версия** — `1.10.2`. Тег `v1.10.1` не трогаем.
2. **Регрессионный тест** — свой, в `tests/error-result`. Тест из форка автора не берём.
3. **Ответ в issue** — пишем после исправления: тезисно, живым языком. Объясняем, что принято и
   почему для числа выбрано `-1`, а не `0`. Публикуем после согласования текста.

## 6. План реализации

Каждый шаг меняет минимум файлов. После каждого шага с кодом — сборка; после шагов 3–4 — тест.

**Шаг 1. Регрессионный тест (до исправления).**
Новый каталог `tests/error-result`: `CMakeLists.txt` и `main.cpp`. Хост компоненты берём из
`tests/native-harness/addin_host.cpp`, копировать его не нужно: CMake подключает файл по
относительному пути. Зависимостей, кроме заголовков `include/`, нет: ни Boost, ни librdkafka.
`AddIn::call` возвращает `Value`, где тип совпадает с типом `tVariant` (`VTYPE_I4` — `int32_t`,
`VTYPE_R8` — `double`, `VTYPE_PWSTR` — `std::string`, `VTYPE_EMPTY` — `std::monostate`), поэтому
тест проверяет и тип, и значение. Сценарии — AC-1–AC-7. Тест прогоняется на текущей DLL и
должен упасть на AC-1–AC-6: так подтверждаем, что он ловит дефект.

**Шаг 2. Признаки типа** — `src/Component.h`: убрать `!` у `returns_bool` и `returns_int32_t`,
добавить поля `returns_string` и `returns_double` в `MethodMeta` и их вычисление в `AddMethod`.

**Шаг 3. Значение ошибки и текст** — `src/Component.cpp`, `CallAsFunc`: ветки для строки и
числа, `msg_err = ...` вместо `+=`. Сборка, тест: AC-1–AC-7 зелёные.

**Шаг 4. Версия** — `src/SimpleKafka1C.h`: `Version` = `1.10.2`. Сборка, повторный тест.

**Шаг 5. Документация** — `docs/exceptionHandling.md` (раздел 2.4) и `CHANGELOG.md`: раздел
`## [1.10.2]` с подразделом «Исправлено» и ссылка внизу файла.

**Шаг 6. Ответ в issue #95** — черновик в чат на согласование; после одобрения — `gh issue comment`.

Коммит — только по команде пользователя.
