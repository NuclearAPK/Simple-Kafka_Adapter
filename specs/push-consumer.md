# Спецификация: Push-consumer (доставка сообщений внешними событиями 1С)

Статус: реализовано 2026-10-12 (шаги 1–6, сборки Windows и Linux); ручная проверка AC-1…AC-11 не выполнена
Дата: 2026-10-12
Версия компоненты: 1.9.5 (не повышается)

## 1. Цель

Сейчас чтение сообщений только синхронное: 1С сама опрашивает брокер через
`ПрочитатьСообщение` / `ЧитатьПакетСообщений`, и вызов блокирует поток 1С на время ожидания.
Нужен режим, в котором компонента читает сообщения в фоновом потоке и передаёт их в 1С
внешним событием (`IAddInDefBase::ExternalEvent`). Клиентская форма при этом не блокируется
и не требует обработчика ожидания.

Инфраструктура уже есть: `Component::ExternalEvent`, `SetEventBufferDepth`,
`GetEventBufferDepth` (`src/Component.cpp:301-325`), но нигде не вызываются.

## 2. Ограничения платформы

1. Внешние события обрабатываются только в клиентском контексте: процедура
   `ОбработкаВнешнегоСобытия(Источник, Событие, Данные)` в модуле формы или модуле
   управляемого приложения (тонкий или толстый клиент). На сервере (rphost, фоновые и
   регламентные задания) обработчика нет — режим там неприменим. Это фиксируется в документации.
2. Веб-клиент не поддерживается (Native API там не работает).
3. Событие передаёт только три строки. Сообщения передаются JSON-ом в параметре `Данные`.
4. Очередь событий платформы ограничена глубиной буфера (по умолчанию 1). Когда буфер полон,
   `ExternalEvent` возвращает `false` и событие не ставится в очередь.

## 3. Новые методы

| Английское имя | Русское имя | Параметры | Возврат |
|---|---|---|---|
| `StartPushConsumer` | `ЗапуститьФоновоеЧтение` | `МаксСообщенийВСобытии` (Число, по умолчанию 100), `МаксОжиданиеМс` (Число, по умолчанию 1000), `КакBase64` (Булево, по умолчанию Ложь), `ГлубинаБуфераСобытий` (Число, по умолчанию 100) | Булево |
| `StopPushConsumer` | `ОстановитьФоновоеЧтение` | — | Булево |
| `IsPushConsumerRunning` | `ФоновоеЧтениеЗапущено` | — | Булево |

Порядок работы в 1С: `ИнициализироватьКонсьюмера` → `Подписаться` (или `НазначитьПартиции`) →
`ЗапуститьФоновоеЧтение` → события → `ОстановитьФоновоеЧтение` → `ОстановитьКонсьюмера`.

## 4. События

`Источник` всегда `"SimpleKafka"`.

| Событие | Когда | Данные |
|---|---|---|
| `Messages` | накоплен пакет: `МаксСообщенийВСобытии` сообщений или истекло `МаксОжиданиеМс` при непустом пакете | JSON в формате `ЧитатьПакетСообщений`: `{"messages":[...],"count":N}` |
| `Error` | ошибка `consume`, кроме `ERR__TIMED_OUT` и `ERR__PARTITION_EOF` | текст ошибки librdkafka |
| `Stopped` | фоновый поток завершился сам из-за фатальной ошибки | текст причины |

Пустые пакеты не отправляются. Формат пакета общий с `ЧитатьПакетСообщений` — код
сериализации выносится в общую функцию, чтобы форматы не разошлись.

## 5. Поведение

### 5.1. Переполнение буфера событий

Если `ExternalEvent` вернул `false`, поток не теряет пакет: повторяет отправку того же пакета
с паузой 100 мс до успеха или до остановки. Новые сообщения из Kafka в это время не читаются
(естественное обратное давление). При остановке в этом состоянии неотправленный пакет
отбрасывается; при `enable.auto.commit=false` его смещения не зафиксированы и будут прочитаны
повторно.

### 5.2. Фиксация смещений

Поведение фиксации не меняется и задаётся настройками librdkafka:

- по умолчанию (`enable.auto.commit=true`) смещения фиксируются автоматически — возможна потеря
  сообщений, если клиент завершится до обработки события;
- для at-least-once пользователь задаёт `enable.auto.commit=false` и вызывает
  `ЗафиксироватьСмещение` из обработчика события. Вызов из потока 1С параллельно с `consume`
  в фоновом потоке допустим: дескриптор librdkafka потокобезопасен.

### 5.3. Блокировка конфликтующих методов

Пока фоновое чтение запущено, методы, которые сами читают сообщения или меняют подписку,
возвращают ошибку `"Push consumer is running"` (Ложь / пустую строку) без обращения к брокеру:
`ПрочитатьСообщение`, `Слушать` (устаревший `consume`), `ЧитатьПакетСообщений`,
`Подписаться`, `НазначитьПартиции`, `ОтменитьНазначение`.

`ИнициализироватьКонсьюмера` и `ОстановитьКонсьюмера` при запущенном чтении сначала
останавливают его, затем выполняют своё действие.

Методы позиционирования (`ЗафиксироватьСмещение`, `УстановитьПозициюЧтения`, `seekTo*`)
не блокируются.

### 5.4. Потоки и время жизни

- `ExternalEvent` из фонового потока вызывается с собственными буферами `WCHAR_T`, без
  `IMemoryManager` (его потокобезопасность не гарантирована).
- Остановка: флаг `std::atomic<bool>`, ожидание завершения потока (`join`). Поток проверяет флаг
  между вызовами `consume` с коротким таймаутом (не больше `МаксОжиданиеМс` и не больше 500 мс),
  поэтому остановка занимает не более ~500 мс плюс время текущей повторной отправки.
- Деструктор компоненты останавливает фоновое чтение до `stopConsumer()`.
- `msg_err` фоновый поток не трогает. Ошибки идут событием `Error` и в лог консьюмера;
  метрики консьюмера (атомарные) обновляются как при синхронном чтении.
- Глубина буфера задаётся `SetEventBufferDepth` в `ЗапуститьФоновоеЧтение` (в потоке 1С).

## 6. Use Cases

**UC-1.** Клиентская форма-монитор подписывается на топик и показывает сообщения по мере
поступления, не блокируя интерфейс.

**UC-2.** Обработка с ручной фиксацией: пользователь обрабатывает пакет в
`ОбработкаВнешнегоСобытия` и фиксирует смещение последнего сообщения пакета.

## 7. Критерии приёмки

**AC-1. Запуск без консьюмера.**
Given консьюмер не инициализирован,
When вызывается `ЗапуститьФоновоеЧтение`,
Then возвращается Ложь и `ПолучитьСообщениеОбОшибке` = `"Consumer not initialized"`.

**AC-2. Повторный запуск.**
Given фоновое чтение запущено,
When `ЗапуститьФоновоеЧтение` вызывается снова,
Then возвращается Ложь с ошибкой `"Push consumer is already running"`, работающий поток не затронут.

**AC-3. Доставка пакета.**
Given консьюмер подписан на топик и фоновое чтение запущено с `МаксСообщенийВСобытии=10`,
When в топик отправлено 25 сообщений,
Then в `ОбработкаВнешнегоСобытия` приходят события `Messages` с суммарным `count` = 25,
ни в одном событии `count` > 10, порядок сообщений в партиции сохранён.

**AC-4. Нет пустых событий.**
Given фоновое чтение запущено, сообщений в топике нет,
When проходит 5 × `МаксОжиданиеМс`,
Then ни одного события `Messages` не приходит.

**AC-5. Формат совпадает с ЧитатьПакетСообщений.**
Given одно и то же сообщение (с ключом, заголовками и бинарным телом),
When оно прочитано через событие и через `ЧитатьПакетСообщений` с тем же `КакBase64`,
Then JSON элемента `messages` совпадает.

**AC-6. Обратное давление.**
Given `ГлубинаБуфераСобытий=1` и клиент не обрабатывает события (модальный диалог),
When в топик поступают сообщения,
Then после закрытия диалога приходят все сообщения без пропусков.

**AC-7. Блокировка конфликтующих методов.**
Given фоновое чтение запущено,
When вызывается `ПрочитатьСообщение` или `ЧитатьПакетСообщений`,
Then возвращается Ложь / пустая строка с ошибкой `"Push consumer is running"`.

**AC-8. Остановка.**
Given фоновое чтение запущено,
When вызывается `ОстановитьФоновоеЧтение`,
Then метод возвращает Истина не позднее чем через 1 с, `ФоновоеЧтениеЗапущено` = Ложь,
после этого событий `Messages` не приходит, синхронное чтение снова доступно.

**AC-9. Закрытие формы без остановки.**
Given фоновое чтение запущено,
When форма закрывается и объект компоненты уничтожается,
Then процесс клиента не падает, поток завершён до удаления консьюмера.

**AC-10. Ручная фиксация.**
Given `enable.auto.commit=false`, фоновое чтение запущено,
When в обработчике события вызывается `ЗафиксироватьСмещение` для последнего сообщения пакета,
Then смещение группы (`ПолучитьСмещенияГруппы`) равно offset + 1, ошибок нет.

**AC-11. Ошибка брокера.**
Given фоновое чтение запущено,
When брокер становится недоступен,
Then приходит событие `Error` с текстом librdkafka; поток продолжает работу и
возобновляет доставку после восстановления брокера.

## 10. План реализации

Каждый шаг заканчивается сборкой Release (`vcvars64.bat` + `cmake --build out/build/x64-Release --config Release`).
Модульных тестов в репозитории нет. Критерии приёмки проверяются вручную на брокере из клиентской формы 1С (шаг 7).

### Шаг 1. Потокобезопасная отправка события — `src/Component.h`, `src/Component.cpp`

Существующий `Component::ExternalEvent` для фонового потока не годится:
- `toUTF16String` использует `static std::wstring_convert`, а он не потокобезопасен;
- строки выделяются через `IMemoryManager`, потокобезопасность которого не гарантирована.

Добавить защищённый метод `bool ExternalEventFromThread(const std::string& src, const std::string& msg, const std::string& data)`:
- UTF-8 → UTF-16 перекодируется локальной функцией без статического состояния;
- буферы `std::u16string` живут на стеке и передаются в `connection->ExternalEvent` через `reinterpret_cast<WCHAR_T*>`;
- вызов `connection->ExternalEvent` под `std::mutex` компоненты, если `connection != nullptr`.

`WCHAR_T` двухбайтовый на обеих платформах (`wchar_t` на Windows, `char16_t` на Linux).

### Шаг 2. Общая сериализация сообщения — `src/consumer_methods.cpp`, `src/SimpleKafka1C.h`

Вынести тело цикла `consumeBatch` (строки 603–688) в
`boost::json::object messageToJson(RdKafka::Message& msg, bool asBase64)`.
`consumeBatch` переключить на неё, поведение не меняется. Это обеспечивает AC-5.

### Шаг 3. Состояние и фоновый поток — новый `src/push_consumer.cpp`, `src/SimpleKafka1C.h`, `CMakeLists.txt`

В `SimpleKafka1C.h` добавить:
```cpp
struct PushConsumerState {
    std::thread worker;
    std::atomic<bool> stopRequested{false};
    std::atomic<bool> running{false};
    std::mutex mtx;                   // for cv
    std::condition_variable cv;       // wakes retry sleep on stop
    int32_t maxMessages = 100;
    int32_t maxWaitMs = 1000;
    bool asBase64 = false;
};
PushConsumerState pushState;
```
и методы `startPushConsumer`, `stopPushConsumer`, `isPushConsumerRunning`, `pushConsumerLoop`,
`bool pushConsumerActive(const char* method)` (ставит `msg_err = "Push consumer is running"`).

Логика потока `pushConsumerLoop`:
1. Пока не запрошена остановка, набирать пакет: `hConsumer->consume(min(осталось до дедлайна, 500))`.
   - `ERR_NO_ERROR`: добавить `messageToJson`, обновить метрики;
   - `ERR__TIMED_OUT` и `ERR__PARTITION_EOF`: продолжать;
   - `ERR__FATAL`: событие `Stopped` с текстом, выход из цикла;
   - иное: событие `Error` (одна попытка отправки), `errorsCount++`, запись в лог консьюмера.
2. Непустой пакет сериализовать в `{"messages":[...],"count":N}` и отправлять `Messages`.
   Пока `ExternalEventFromThread` возвращает `false` и остановка не запрошена, ждать на `cv` 100 мс и повторять.
3. На выходе `running = false`.

`startPushConsumer(maxMessages, maxWaitMs, asBase64, bufferDepth)`:
- проверяет консьюмер (AC-1) и повторный запуск (AC-2);
- валидирует параметры: все > 0;
- делает `join` ранее завершившегося потока;
- вызывает `SetEventBufferDepth(bufferDepth)`;
- запускает `std::thread`.

`stopPushConsumer()`: `stopRequested = true`, `cv.notify_all()`, `join`. Идемпотентен.

Файл добавить в `SOURCE_FILES` в `CMakeLists.txt`.

### Шаг 4. Регистрация и интеграция — `src/SimpleKafka1C.cpp`, `src/consumer_methods.cpp`

- `AddMethod` для трёх методов, значения по умолчанию `{ {0, 100}, {1, 1000}, {2, false}, {3, 100} }`.
- Охранные проверки `pushConsumerActive()` в начале `getMessage`, `consume`, `consumeBatch`, `subscribe`, `assign`, `unassign` (AC-7).
- `initConsumer` и `stopConsumer`: первым действием `stopPushConsumer()`.
- Деструктор: `stopPushConsumer()` до `stopConsumer()`.
- Переопределить `Done()` в `SimpleKafka1C` и вызывать там `stopPushConsumer()`, потому что после `Done` указатель `connection` недействителен (AC-9).

### Шаг 5. Сверка с librdkafka

Перед финальной сборкой сверить с `rdkafkacpp.h` и документацией librdkafka (Context7 / DeepWiki):
- допустимость `commitSync` / `seek` / `assignment` из потока 1С параллельно с `consume` в фоновом потоке;
- то, что `rebalance_cb` и `event_cb` вызываются из потока, который делает `consume`, то есть из фонового;
- код фатальной ошибки `ERR__FATAL` для консьюмера.

Если какая-то операция окажется недопустимой параллельно, добавить её в блокируемые методы (п. 5.3 спеки) с отметкой в спеке.

## 11. Итоги реализации

- Шаг 5 (сверка с librdkafka, INTRODUCTION.md, раздел «Threads and callbacks»): API полностью потокобезопасен, поэтому `commitSync`, `seek` и `assignment` можно вызывать из потока 1С параллельно с `consume`. Callbacks, которые обслуживаются через poll (`event_cb`, `rebalance_cb`), вызываются в потоке, выполняющем `consume`, то есть в фоновом. Оба уже защищены (`AsyncErrorState::mtx`, `clRebalanceCb::offsetsMtx`). Список блокируемых методов не расширялся.
- `openEventFile` читает поля `cl_event_cb`, которые `initProducer` может переписать из потока 1С. Поэтому фоновый поток берёт настройки лога из снимка, сделанного при запуске (`PushConsumerState::logDir/logFormat/clientId`).
- Если пакет пуст к концу `МаксОжиданиеМс`, окно ожидания перезапускается. Так первое сообщение после простоя не уходит в 1С отдельным событием сразу после истечения старого окна.
- Сборки: Windows x64 Release (MSVC) и Linux WSL Ubuntu 24.04 прошли без ошибок и без предупреждений в изменённых файлах.
