# 1.10.1: увеличение числа партиций, приостановка и возобновление чтения

Статус: реализовано 2026-10-15 (шаги 1–4), не закоммичено.
Версия компоненты: 1.10.1 (вместе с исправлениями из `specs/fixes-1.10.1.md`).

## 1. Цель

Добавить две возможности librdkafka, которых нет в компоненте:

1. Увеличение числа партиций существующего топика (`rd_kafka_CreatePartitions`). Сейчас число
   партиций задаётся только при `СоздатьТопик`.
2. Приостановка и возобновление чтения отдельных партиций обычного консьюмера
   (`KafkaConsumer::pause` / `resume`). Сейчас остановить поток сообщений можно только через
   `ОстановитьКонсьюмера`. Это выход из группы и ребалансировка у всех участников.

## 2. Use cases

- **UC-1.** Нагрузка на топик выросла, нужно больше параллельных консьюмеров. Администратор
  увеличивает число партиций из 1С без консольных утилит Kafka.
- **UC-2.** Обработчик сообщений зависит от внешней системы, а она недоступна. Код 1С
  приостанавливает чтение и остаётся в группе: партиции не уходят другим консьюмерам,
  ребалансировки нет. Когда система вернулась, код возобновляет чтение с того же места.
- **UC-3.** Одна партиция содержит «тяжёлые» сообщения. Её чтение приостанавливается, а
  остальные партиции читаются дальше.

## 3. Требуемое поведение

### 3.1. `УвеличитьЧислоПартиций` / `CreatePartitions`

```1c
УвеличитьЧислоПартиций(Брокеры, Топик, ЧислоПартиций, Таймаут = 10000)
```

- `ЧислоПартиций` — новое **общее** число партиций, а не прирост.
- Возврат: Истина — партиции созданы. Ложь — ошибка в `ПолучитьСообщениеОбОшибке`.
- Проверки до запроса, как в `СоздатьТопик`: адрес брокеров, имя топика, `ЧислоПартиций > 0`.
- Ошибка брокера возвращается текстом из `rd_kafka_topic_result_error_string`. Примеры:
  число не больше текущего (`INVALID_PARTITIONS`), топика нет (`UNKNOWN_TOPIC_OR_PART`).
- Таймаут передаётся как `operation_timeout` (брокер ждёт создания партиций) и как
  `request_timeout`. Ожидание ответа — `Таймаут + 2000` мс, как в остальных Admin-методах.
- Уменьшить число партиций Kafka не позволяет. В документации об этом есть предупреждение и
  о смене соответствия «ключ → партиция» для сообщений с ключом.

### 3.2. `ПриостановитьЧтение` / `PauseConsumption` и `ВозобновитьЧтение` / `ResumeConsumption`

```1c
ПриостановитьЧтение(Топик = "", Партиция = -1)
ВозобновитьЧтение(Топик = "", Партиция = -1)
```

- Область действия:
  - `Топик` пустой — все партиции, назначенные консьюмеру;
  - задан только `Топик` — все назначенные партиции этого топика;
  - заданы `Топик` и `Партиция` — одна партиция.
- Возврат Истина или Ложь. Ошибки:
  - консьюмер не инициализирован;
  - указанная партиция не назначена консьюмеру;
  - под область не попала ни одна назначенная партиция (например, вызов до первого
    назначения после `Подписаться`);
  - ошибка librdkafka по партиции (текст с топиком и номером партиции).
- После `ПриостановитьЧтение` сообщения приостановленных партиций не возвращаются ни одним
  методом чтения: `ПолучитьСообщение`, `ЧитатьПакетСообщений` и фоновое чтение (push-режим).
  Это относится и к сообщениям, которые librdkafka уже скачала в локальную очередь.
- Консьюмер остаётся в группе, ребалансировки нет. Смещения не меняются.
- После `ВозобновитьЧтение` чтение продолжается со следующего непрочитанного сообщения, без
  потерь и без повторов.
- Повторная пауза приостановленной партиции и возобновление не приостановленной — не ошибка.
- Пауза привязана к консьюмеру и партиции. Она действует до `ВозобновитьЧтение` или
  `ОстановитьКонсьюмера`, в том числе если партиция при ребалансировке ушла и вернулась к
  этому консьюмеру. Компонента запоминает приостановленные партиции и после каждого
  назначения повторно ставит их на паузу. Партиция, перешедшая к другому консьюмеру, у него
  читается.
- Методы потокобезопасны относительно фонового чтения и обработчика ребалансировки.
- Читателя очереди (share consumer) методы не затрагивают.

## 4. Критерии приёмки

Стенд: `docker/kafka-share`. Проверки — в `tests/native-harness`, идентификаторы `CP-*` и `PR-*`.

**CP-1. Увеличение числа партиций**
Given топик с 2 партициями
When `УвеличитьЧислоПартиций(Брокеры, Топик, 4)`
Then Истина; `ПолучитьМетаданныеТопика` показывает 4 партиции; сообщение, отправленное в
партицию 3, читается консьюмером.

**CP-2. Число не больше текущего**
Given топик с 4 партициями
When `УвеличитьЧислоПартиций(..., 4)` и `УвеличитьЧислоПартиций(..., 3)`
Then оба вызова — Ложь, ошибка от брокера; партиций по-прежнему 4.

**CP-3. Неверные аргументы**
When `ЧислоПартиций = 0`; топика не существует
Then Ложь и текст ошибки.

**PR-1. Пауза одной партиции**
Given консьюмер читает топик с 2 партициями
When `ПриостановитьЧтение(Топик, 0)`, затем в обе партиции пишутся сообщения
Then читаются только сообщения партиции 1. После `ВозобновитьЧтение(Топик, 0)` приходят все
сообщения партиции 0, каждое ровно один раз.

**PR-2. Уже скачанные сообщения**
Given в партиции 0 10 сообщений, консьюмер прочитал 1 (остальные в локальной очереди)
When `ПриостановитьЧтение(Топик, 0)` и чтение в течение 3 с
Then сообщений партиции 0 нет. После `ВозобновитьЧтение` приходят оставшиеся 9, без повторов.

**PR-3. Пауза всех партиций**
When `ПриостановитьЧтение()`
Then чтение в течение 3 с ничего не возвращает. После `ВозобновитьЧтение()` приходят все
сообщения.

**PR-4. Ошибки**
- консьюмер не инициализирован — Ложь;
- партиция не назначена (номер 5 у топика с 2 партициями) — Ложь, ошибка называет партицию;
- в обоих случаях текст в `ПолучитьСообщениеОбОшибке`.

**PR-5. Пауза переживает ребалансировку**
Given A приостановил партицию 0 топика с 2 партициями
When в группу входит B, затем выходит, и партиция 0 возвращается к A
Then A не читает партицию 0 до `ВозобновитьЧтение`, после него читает.
Проверка на протоколе по умолчанию и на `cooperative-sticky`.

**PR-6. Регрессия**
Полный прогон harness (включая FIX-*) на Windows и Linux — без ошибок.

«Broker: Unknown topic or partition».

### Шаг 3. Приостановка и возобновление
- `src/consumer_methods.cpp`: `pauseConsumption` / `resumeConsumption`. Область собирается
  из `hConsumer->assignment()`, затем `pause` / `resume` и разбор ошибок по партициям.
- `src/SimpleKafka1C.h`, `src/SimpleKafka1C.cpp`:
  - множество приостановленных партиций в `clRebalanceCb` под его мьютексом;
  - `rebalance_cb` после назначения повторно ставит на паузу партиции из множества;
  - `ОстановитьКонсьюмера` очищает множество;
  - регистрация методов со значениями по умолчанию `{ {0, ""}, {1, -1} }`.
- Проверка: PR-1…PR-5.

Итог (выполнен 2026-10-15):
- `setConsumptionPaused` в `src/consumer_methods.cpp`: область из `assignment()`, `pause` /
  `resume`, ошибки по партициям. `ВозобновитьЧтение` для топика или всех партиций очищает
  запомненные паузы и для партиций, не назначенных сейчас. `ОстановитьКонсьюмера` очищает
  множество.
- `rebalance_cb` после успешного назначения ставит на паузу партиции из множества.
- PR-1…PR-5c: 97 проверок, 0 ошибок; FIX-5/6 без регрессии.
- Наблюдение: с отключённой повторной паузой PR-5 и PR-5c тоже проходят — librdkafka 2.16.0
  сама сохраняет флаг паузы приложения (`RD_KAFKA_TOPPAR_F_APP_PAUSE`) при снятии и повторном
  назначении партиции; `assign` сбрасывает только флаг библиотеки. Повторная пауза в
  компоненте — страховка на случай пересоздания партиции в librdkafka или смены поведения
  в будущих версиях; harness её отдельно не проверяет.
